### 前言

到目前为止，我们一直在用 `&T` 引用来借用数据。绝大多数场景下这就够了——借用检查器帮你保证安全，编译器帮你管理生命周期，一切都在栈上搞定。

但有些场景，普通引用真的不够用：

- **需要堆分配**：数据大小在编译期未知，或者你就是想把数据放堆上
- **需要共享所有权**：多个部分同时持有同一份数据的所有权，不知道谁最后释放
- **需要内部可变性**：你有一个不可变引用，但就是需要修改里面的某个字段

这些需求催生了 Rust 的**智能指针**（smart pointer）。智能指针不仅仅是一个地址——它们是拥有额外元数据和行为的结构体，实现了 `Deref` 和 `Drop` trait，让它们表现得像引用一样，但又有自己的超能力。

如果你是 JS 开发者，其实你一直在用"智能指针"——JS 的引用计数垃圾回收、对象始终在堆上——这些在 Rust 中都变成了显式的选择。

这篇我们来聊 `Box<T>`、`Rc<T>`、`RefCell<T>` 这三个最常用的智能指针，以及它们的组合使用方式。

<DividerLarge />

## Box\<T\> —— 堆上分配

### 什么是 Box

`Box<T>` 是最简单的智能指针——它把数据放到**堆**上，自己在栈上存一个指向堆数据的指针。当 `Box` 离开作用域时，堆上的数据也会被自动释放。

```rust

fn main() {
    let x = Box::new(42);       // 42 被分配到堆上
    println!("x = {}", x);      // 像普通值一样使用
    println!("x = {}", *x);     // 显式解引用也行
}
// x 离开作用域，堆上的 42 被释放

```

你可能会问：一个 `i32` 放堆上有什么意义？确实，对于简单类型，`Box` 没什么优势。它真正发挥作用的场景有三个：

1. **编译期大小未知**的类型（递归类型）
2. **大量数据转移所有权**时，避免栈上拷贝
3. **trait 对象**（`Box<dyn Trait>`）

<DividerSmall />

### JS 和 Rust 的内存分配对比

在 JS 中，你从来不需要想"这个数据放栈上还是堆上"——因为所有对象都在堆上，引擎替你决定一切。Rust 则把这个选择权交给了你。

<CodeComparison

  right={{ title: "Rust", language: "rust", code: `// Rust 中你显式选择堆分配\nlet obj = Box::new(User { name: String::from("Clark") });\n// 栈上存指针，堆上存数据` }}
  description="JS 隐式堆分配，Rust 显式控制——Box 让你主动选择"
/>

这种显式控制的好处是**可预测性**。你清楚地知道每一个字节在哪里，什么时候分配，什么时候释放。代价是你需要多想一步——但编译器会帮你检查。

<DividerSmall />

### 递归类型：Box 的经典用例

来看 `Box` 最常见的用途——定义递归数据结构。试试不用 `Box` 定义一个链表：

```rust

// ❌ 编译失败！
enum List {
    Cons(i32, List),   // List 里面包含 List
    Nil,
}

```

编译器会报错：`recursive type has infinite size`。为什么？因为编译器需要在编译期知道每个类型的大小。`List` 包含一个 `List`，那个 `List` 又包含一个 `List`……无穷嵌套，大小无限。

用 `Box` 解决：

```rust

enum List {
    Cons(i32, Box<List>),  // Box 的大小是固定的（一个指针）
    Nil,
}

fn main() {
    let list = List::Cons(1,
        Box::new(List::Cons(2,
            Box::new(List::Cons(3,
                Box::new(List::Nil)
            ))
        ))
    );
    // 链表：1 -> 2 -> 3 -> Nil
}

```

`Box<List>` 的大小永远是一个指针（在 64 位系统上是 8 字节），不管它指向的 `List` 嵌套了多少层。编译器现在能算出 `List` 的大小了：一个 `i32`（4 字节）加一个 `Box`（8 字节），再加上 enum 标签。

> [!TIP]
> 在 JS 中你可以随手写递归结构：`{ value: 1, next: { value: 2, next: null } }`——因为 JS 对象本身就是堆分配的引用类型，天然就是一个"指针"。Rust 要求你用 `Box` 把这层间接引用显式写出来。多写几个字，换来的是零运行时开销和编译期大小确定。

<DividerSmall />

### Trait 对象：Box\<dyn Trait\>

另一个常见用途是用 `Box` 来创建 trait 对象——当你想把实现了同一个 trait 的不同类型放在同一个集合里时：

```rust

trait Animal {
    fn speak(&self) -> String;
}

struct Dog;
struct Cat;

impl Animal for Dog {
    fn speak(&self) -> String {
        String::from("汪汪！")
    }
}

impl Animal for Cat {
    fn speak(&self) -> String {
        String::from("喵喵！")
    }
}

fn main() {
    // Vec<Box<dyn Animal>> —— 不同类型，统一接口
    let animals: Vec<Box<dyn Animal>> = vec![
        Box::new(Dog),
        Box::new(Cat),
        Box::new(Dog),
    ];

    for animal in &animals {
        println!("{}", animal.speak());
    }
    // 汪汪！
    // 喵喵！
    // 汪汪！
}

```

`dyn Animal` 意味着"任何实现了 `Animal` trait 的类型"。因为不同类型大小不同（`Dog` 和 `Cat` 的内存布局可能不一样），编译器不知道该分配多少空间，所以你需要 `Box` 把它们包起来——统一成一个指针大小。

这有点像 JS 中的接口或鸭子类型——你只关心对象有没有 `speak` 方法，不关心它是什么类型。只不过 Rust 把这种"多态"的代价（堆分配 + 虚表查找）显式地写出来了。

## Deref 与 Drop trait

智能指针之所以"智能"，是因为它们实现了两个关键 trait：`Deref` 和 `Drop`。搞懂这两个 trait，你就理解了智能指针的核心机制。

<DividerSmall />

### Deref：让智能指针像引用一样使用

`Deref` trait 让你可以用 `*` 运算符解引用一个智能指针，就像对普通引用一样：

```rust

use std::ops::Deref;

fn main() {
    let x = 5;
    let y = &x;         // y 是一个引用
    let z = Box::new(x); // z 是一个 Box 智能指针

    assert_eq!(5, *y);  // 解引用普通引用
    assert_eq!(5, *z);  // 解引用 Box——因为 Box 实现了 Deref
}

```

`Box` 实现了 `Deref`，所以 `*z` 在底层实际上调用了 `*(z.deref())`。这让你几乎可以在所有需要引用的地方直接用 `Box`。

<DividerSmall />

### 解引用强制转换（Deref Coercion）

`Deref` 还有一个超级实用的魔法——**解引用强制转换**。当函数参数需要 `&T` 而你传入了 `&Box<T>` 时，Rust 会自动帮你转换：

```rust

fn greet(name: &str) {
    println!("Hello, {}!", name);
}

fn main() {
    let name = Box::new(String::from("Clark"));

    // name 的类型是 Box<String>
    // &name 的类型是 &Box<String>
    // Rust 自动转换链：&Box<String> -> &String -> &str
    greet(&name);  // ✅ 直接传，Rust 自动解引用
}

```

Rust 会沿着 `Deref` 链一路转换下去，直到找到匹配的类型。这就是为什么你可以把 `&String` 传给需要 `&str` 的函数——因为 `String` 实现了 `Deref<Target = str>`。

> [!NOTE]
> 解引用强制转换只在编译期发生，完全零成本。你不需要手动写 `&*name` 或者 `name.as_str()` 这种繁琐的转换——Rust 编译器会自动帮你。

<DividerSmall />

### Drop：离开作用域时自动清理

`Drop` trait 让你自定义当值离开作用域时要做什么。对于智能指针来说，这通常意味着释放堆内存：

```rust

struct MyBox<T> {
    data: T,
}

impl<T> Drop for MyBox<T> {
    fn drop(&mut self) {
        println!("正在释放 MyBox 中的数据！");
    }
}

fn main() {
    let a = MyBox { data: String::from("hello") };
    let b = MyBox { data: String::from("world") };
    println!("MyBox 已创建");
}
// 输出：
// MyBox 已创建
// 正在释放 MyBox 中的数据！  <- b 先被释放
// 正在释放 MyBox 中的数据！  <- 然后 a 被释放

```

注意 **drop 的顺序是反过来的**——后创建的先销毁，就像栈一样（LIFO）。这是有道理的：后创建的变量可能依赖先创建的变量，所以先清理它们更安全。

如果你想提前释放（不等到作用域结束），用 `std::mem::drop`：

```rust

fn main() {
    let data = Box::new(42);
    println!("data = {}", data);

    drop(data);  // 手动提前释放

    // println!("{}", data); // ❌ data 已经被释放了
    println!("data 已提前释放");
}

```

> [!WARNING]
> 你不能直接调用 `data.drop()`——Rust 禁止手动调用 `Drop::drop` 方法，因为 Rust 在作用域结束时还会自动调用一次，导致**双重释放**（double free）。用 `std::mem::drop` 函数来代替，它会转移所有权并触发 drop。

## Rc\<T\> —— 引用计数

### 共享所有权的需求

Rust 的所有权规则是"一个值只有一个所有者"。但有些场景确实需要多个所有者——比如图数据结构中一个节点可能被多条边引用，或者多个组件需要共享同一份配置数据。

`Rc<T>`（Reference Counting，引用计数）就是为这种场景设计的。它内部维护一个计数器，记录有多少个 `Rc` 指向同一份数据。只有当最后一个 `Rc` 被销毁时，数据才真正被释放。

```rust

use std::rc::Rc;

fn main() {
    let a = Rc::new(String::from("hello"));
    println!("创建后，引用计数 = {}", Rc::strong_count(&a)); // 1

    let b = Rc::clone(&a);  // 克隆 Rc，不是克隆数据！
    println!("b 克隆后，引用计数 = {}", Rc::strong_count(&a)); // 2

    let c = Rc::clone(&a);
    println!("c 克隆后，引用计数 = {}", Rc::strong_count(&a)); // 3

    {
        let d = Rc::clone(&a);
        println!("d 克隆后，引用计数 = {}", Rc::strong_count(&a)); // 4
    } // d 离开作用域，计数减 1

    println!("d 释放后，引用计数 = {}", Rc::strong_count(&a)); // 3
}

```

`Rc::clone(&a)` 并不会深拷贝数据——它只是把引用计数加 1，开销非常小。这和 JS 中多个变量指向同一个对象很像，只不过 JS 的引用计数是引擎内部管理的，你看不到。

### 用 Rc 实现共享数据

来看一个实际的例子——两个列表共享同一个尾部：

```rust

use std::rc::Rc;

enum List {
    Cons(i32, Rc<List>),
    Nil,
}

use List::{Cons, Nil};

fn main() {
    // 共享的尾部：3 -> Nil
    let shared_tail = Rc::new(Cons(3, Rc::new(Nil)));

    // 两个列表共享同一个尾部
    let list_a = Cons(1, Rc::clone(&shared_tail)); // 1 -> 3 -> Nil
    let list_b = Cons(2, Rc::clone(&shared_tail)); // 2 -> 3 -> Nil

    println!("shared_tail 的引用计数: {}", Rc::strong_count(&shared_tail)); // 3
}

```

如果不用 `Rc`，你要么克隆整个尾部（浪费内存），要么用引用（但生命周期会搞得你头疼）。`Rc` 让多个所有者共享同一份数据变得自然而安全。

<DividerSmall />

### Rc 的限制

> [!WARNING]
> **Rc 是单线程的！** 它内部的引用计数操作不是原子的，所以不能在多线程环境中使用。如果你需要跨线程共享数据，使用 `Arc<T>`（Atomic Reference Counting）。`Arc` 的 API 和 `Rc` 几乎一模一样，只是内部用原子操作保证线程安全。
>
> ```rust
> use std::sync::Arc;
> use std::thread;
>
> let data = Arc::new(vec![1, 2, 3]);
> let data_clone = Arc::clone(&data);
>
> thread::spawn(move || {
>     println!("{:?}", data_clone);
> });
> ```
>
> 选择规则：单线程用 `Rc`，多线程用 `Arc`。`Arc` 因为原子操作会有一点性能开销，所以能用 `Rc` 就别用 `Arc`。

还有一点：**Rc 只能提供不可变引用**。通过 `Rc<T>` 你拿到的永远是 `&T`，没法拿到 `&mut T`。这是刻意设计的——如果多个 `Rc` 都能修改数据，就违反了借用规则（多个可变引用）。

那如果你就是需要在多个 `Rc` 之间修改共享数据怎么办？这就需要我们的下一个主角——`RefCell<T>`。

<DividerLarge />

## RefCell\<T\> —— 内部可变性

### 什么是内部可变性

Rust 的借用规则很严格：同一时刻，要么有多个不可变引用，要么有一个可变引用，不能同时存在。这个规则在**编译期**强制执行，安全但有时候过于保守。

`RefCell<T>` 把这个检查推迟到了**运行时**。它允许你在持有不可变引用的情况下修改内部数据——这就是**内部可变性**（interior mutability）模式。

```rust

use std::cell::RefCell;

fn main() {
    let data = RefCell::new(vec![1, 2, 3]);

    // data 本身没有声明为 mut，但我们可以修改里面的值！
    data.borrow_mut().push(4);

    println!("{:?}", data.borrow()); // [1, 2, 3, 4]
}

```

看到了吗？`data` 不是 `mut` 的，但我们通过 `borrow_mut()` 拿到了可变引用并修改了数据。这在普通引用的世界里是不可能的。

<DividerSmall />

### borrow() 和 borrow_mut()

`RefCell` 提供两个方法来获取引用：

```rust

use std::cell::RefCell;

fn main() {
    let data = RefCell::new(42);

    // borrow() -> Ref<T>：获取不可变引用
    {
        let r1 = data.borrow();
        let r2 = data.borrow();  // ✅ 多个不可变引用，没问题
        println!("r1 = {}, r2 = {}", r1, r2);
    } // r1, r2 离开作用域

    // borrow_mut() -> RefMut<T>：获取可变引用
    {
        let mut r3 = data.borrow_mut();
        *r3 += 1;
        println!("r3 = {}", r3);  // 43
    } // r3 离开作用域

    // ❌ 运行时 panic！同时持有不可变和可变引用
    // let r4 = data.borrow();
    // let r5 = data.borrow_mut(); // 💥 BorrowMutError
}

```

核心区别在于：编译器不会在编译期报错——它在**运行时**检查借用规则。如果你违反了规则（比如同时存在可变和不可变引用），程序会直接 panic。

> [!TIP]
> 编译期检查 vs 运行时检查：
> - 普通引用（`&T` / `&mut T`）：编译器在编译期就拒绝违规代码，完全零成本
> - `RefCell<T>`：编译器放行，在运行时检查。有一点点性能开销（维护借用计数），但更灵活
>
> 大原则是：**能用编译期检查就用编译期检查**。只在编译器过于保守、你确信代码安全的情况下才用 `RefCell`。

<DividerSmall />

### 三种引用方式对比

| 特征 | `&T` / `&mut T` | `RefCell<T>` | `Mutex<T>` |
|------|-----------------|-------------|------------|
| 检查时机 | 编译期 | 运行时 | 运行时 |
| 性能开销 | 零 | 极小（借用计数） | 较大（锁） |
| 线程安全 | 取决于 T | 单线程 | 多线程 |
| 违规后果 | 编译失败 | panic | 死锁或 panic |
| 灵活性 | 较低 | 中等 | 高 |
| 使用场景 | 默认选择 | 内部可变性 | 跨线程共享可变数据 |

<DividerSmall />

### 一个实际的例子：Mock 对象

内部可变性的一个经典应用场景是 mock 对象——在测试中记录方法被调用的情况：

```rust

use std::cell::RefCell;

trait Messenger {
    fn send(&self, msg: &str);
}

struct MockMessenger {
    sent_messages: RefCell<Vec<String>>,
}

impl MockMessenger {
    fn new() -> MockMessenger {
        MockMessenger {
            sent_messages: RefCell::new(vec![]),
        }
    }
}

impl Messenger for MockMessenger {
    fn send(&self, msg: &str) {
        // send 接收 &self（不可变引用）
        // 但我们需要修改 sent_messages 来记录消息
        // RefCell 让这成为可能！
        self.sent_messages.borrow_mut().push(String::from(msg));
    }
}

fn main() {
    let mock = MockMessenger::new();
    mock.send("你好");
    mock.send("世界");

    assert_eq!(mock.sent_messages.borrow().len(), 2);
    println!("发送了 {} 条消息", mock.sent_messages.borrow().len());
}

```

注意 `send` 方法的签名是 `&self`——不可变引用。但我们需要往 `sent_messages` 里 push 数据。如果 `sent_messages` 是普通的 `Vec<String>`，编译器会拒绝。用 `RefCell` 包裹之后，我们就能在 `&self` 的约束下修改内部数据了。

## 常见组合模式

### Rc\<RefCell\<T\>\>：共享且可变

把 `Rc` 和 `RefCell` 组合起来，你就得到了一个**多个所有者都能修改的共享数据**：

- `Rc<T>` 提供多个所有者的能力
- `RefCell<T>` 提供在不可变上下文中修改数据的能力

```rust

use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
struct Node {
    value: i32,
    children: Vec<Rc<RefCell<Node>>>,
}

fn main() {
    // 创建一个共享的子节点
    let child = Rc::new(RefCell::new(Node {
        value: 10,
        children: vec![],
    }));

    // 两个父节点共享同一个子节点
    let parent1 = Node {
        value: 1,
        children: vec![Rc::clone(&child)],
    };

    let parent2 = Node {
        value: 2,
        children: vec![Rc::clone(&child)],
    };

    // 通过任意一个 Rc 修改子节点的值
    child.borrow_mut().value = 99;

    // 两个父节点看到的都是修改后的值
    println!(
        "parent1 的子节点: {:?}",
        parent1.children[0].borrow().value
    ); // 99
    println!(
        "parent2 的子节点: {:?}",
        parent2.children[0].borrow().value
    ); // 99
}

```

这个模式在 Rust 中非常常见——只要你需要"多个地方共享同一份可变数据"，`Rc<RefCell<T>>` 基本上就是答案。

在 JS 中这种共享可变状态是默认行为——多个变量指向同一个对象，任何一个都能修改它。Rust 用 `Rc<RefCell<T>>` 把这种行为显式地写了出来，让你清楚地知道"这里有共享可变状态，要小心"。

<DividerSmall />

### 另一个例子：共享计数器

```rust

use std::cell::RefCell;
use std::rc::Rc;

fn main() {
    let counter = Rc::new(RefCell::new(0));

    // 模拟多个"观察者"共享同一个计数器
    let observer1 = Rc::clone(&counter);
    let observer2 = Rc::clone(&counter);
    let observer3 = Rc::clone(&counter);

    // 每个观察者都能修改计数器
    *observer1.borrow_mut() += 1;
    *observer2.borrow_mut() += 1;
    *observer3.borrow_mut() += 1;

    println!("最终计数: {}", counter.borrow()); // 3
    println!("引用计数: {}", Rc::strong_count(&counter)); // 4
}

```

<DividerSmall />

### 如何选择智能指针

> [!TIP]
> 选择智能指针的决策指南：
>
> 1. **需要堆分配？** -> `Box<T>`
> 2. **需要多个所有者？** -> `Rc<T>`（单线程）或 `Arc<T>`（多线程）
> 3. **需要内部可变性？** -> `RefCell<T>`（单线程）或 `Mutex<T>`（多线程）
> 4. **需要多个所有者 + 可变？** -> `Rc<RefCell<T>>` 或 `Arc<Mutex<T>>`
> 5. **以上都不需要？** -> 直接用普通引用 `&T` / `&mut T`
>
> 大原则：**从最简单的开始**。普通引用够用就不要上 `Box`，`Box` 够用就不要上 `Rc`，`Rc` 够用就不要上 `Rc<RefCell<T>>`。每一层包装都增加了复杂度——只在真正需要时才使用。

<DividerSmall />

### Box vs Rc vs RefCell 对比

| 特征 | `Box<T>` | `Rc<T>` | `RefCell<T>` |
|------|---------|--------|-------------|
| 所有者数量 | 1 个 | 多个 | 1 个 |
| 借用检查 | 编译期 | 编译期 | 运行时 |
| 可变性 | 拥有所有权时可变 | 只能不可变借用 | 可以在不可变上下文中修改 |
| 线程安全 | 是（Send + Sync） | 否 | 否 |
| 典型用途 | 堆分配、递归类型 | 共享所有权 | 内部可变性 |
| 多线程替代 | 无需（本身就线程安全） | `Arc<T>` | `Mutex<T>` |
| 性能开销 | 堆分配 | 堆分配 + 引用计数 | 运行时借用检查 |

<DividerLarge />

### 小结

这篇我们深入了 Rust 的三大智能指针：

- **`Box<T>`** 最简单——把数据放堆上，一个所有者，用于递归类型和 trait 对象
- **`Deref`** 让智能指针像引用一样使用，**`Drop`** 让离开作用域时自动清理资源
- **`Rc<T>`** 通过引用计数实现共享所有权——多个 `Rc` 指向同一份数据，最后一个释放时数据才被清理
- **`RefCell<T>`** 把借用检查从编译期推迟到运行时，提供内部可变性——在 `&self` 约束下修改数据
- **`Rc<RefCell<T>>`** 组合起来实现"多所有者 + 可变"——对应 JS 中对象的默认行为，但 Rust 让你显式选择

如果你从 JS 过来，一个核心观察是：**JS 中默认的一切（堆分配、引用计数、共享可变状态），在 Rust 中都变成了显式的、可选的**。这不是为了折磨你——而是让你在需要性能的时候有"不用"的选项，在需要灵活性的时候有"用"的工具。
